Architectural Philosophy & Compliance
Why banking systems are organized with strict isolation and zero-trust security boundaries.

In Singapore’s banking sector, architectures are heavily governed by the MAS Technology Risk Management (TRM) guidelines. Systems require strict zero-trust network segmentation, multi-factor encryption, and non-repudiation. Unlike tech scale-ups that prioritize raw feature velocity, banks prioritize system resiliency, data consistency (ACID), and immutable auditability.

End-to-End Activity Walkthrough: Fund Transfer
Tracing how a transaction moves from client mobile apps down to core financial ledgers.
Layer 1: Client, Edge & API Gateway Layer

What Happens: The user's mobile app initiates a transfer. Traffic hits Cloudflare WAF and Kong/Apigee API gateways. External traffic never communicates directly with internal bank servers.

Accountable Role: Platform / Infrastructure Engineer 🏷️

Layer 2: Backend Microservices & Orchestration Layer

What Happens: Gateways route requests to internal microservices (`Fund-Transfer-Service` & `Account-Ledger-Service`) built on Java Spring Boot or .NET. Business logic validates limits and balances.

Accountable Role: Backend Software Engineer 🏷️

Layer 3: Security, Encryption & Compliance Zone

What Happens: Payloads pass through Hardware Security Modules (HSM) for cryptographic signing, while SIEM tools (Splunk) capture immutable audit trails for non-repudiation.

Accountable Role: Cybersecurity / SecOps Engineer 🏷️

Layer 4: Core Transaction & Database Layer

What Happens: The transaction is committed to ACID-compliant relational databases (Oracle RAC / PostgreSQL) with Redis handling fast idempotency checks to prevent double-debts.

Accountable Role: Database Administrator / Data Engineer 🏷️
